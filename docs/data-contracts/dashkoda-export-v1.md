# DashKoda export contract, version 1

## Purpose

This is the field-level contract the future application must be able to export
so Koda's existing management reporting keeps working after the Excel register
is retired. **No exporter is built yet** (Stage 4). The contract exists now so
that Stage 1 does not build a schema that cannot serve it.

The contract is versioned. A change to any field's meaning requires a new
version, not an edit to this one.

## Delivery

- A versioned file (CSV or JSON) or an authenticated endpoint, whichever the
  DashKoda owner prefers. Format is an open decision.
- Generated by a scheduled management command from the same application image.
- One row per Matter, plus a separate submissions extract (see below).
- Every export names its contract version and the generation timestamp.

## Row identity

| Field | Source | Notes |
| --- | --- | --- |
| `matter_id` | `Matter.id` | UUIDv7. Stable forever. The join key. |
| `reference` | derived from `Matter.reference_year` + `reference_number` | The familiar `YYYY_N`. Empty for archive rows that never had one. |
| `reporting_year` | `Matter.reporting_year` | Stable reporting identity; does not change when a Matter runs across years. |
| `record_mode` | `Matter.record_mode` | `FULL` or `ARCHIVE`. Consumers must be able to separate them. |
| `origin` | `Matter.origin` | `NATIVE`, `LEGACY_IMPORT`, `PROMOTED_LEGACY`, `OTHER`. |
| `data_quality_tier` | `Matter.data_quality_tier` | Empty when unassessed. |

## Descriptive fields

| Field | Source | Notes |
| --- | --- | --- |
| `title` | `Matter.title` | |
| `owner` | `Matter.owner` | Display name and stable user id. Empty is legitimate. |
| `stage_key` | `Matter.stage.key` | Code-managed vocabulary, not free text. Empty for archive rows. |
| `track` | `Matter.track` | |
| `policy_areas` | `Matter.policy_areas` | Repeated values; a Matter may have several. |
| `tags` | confirmed `TagAssignment` rows only | Machine suggestions are excluded. |
| `source_organisations` | `Matter.source_organisations` | The `KELLELT` direction. Repeated values; a Matter may have several senders. |
| `addressee_organisation` | `Matter.addressee_organisation` | The `KELLELE` direction. Exactly one, or none. |

**Direction rule.** `source_organisations` and `addressee_organisation` are
different facts and must never be merged into one counterparty column, in either
direction, for any era.

**Cardinality rule.** The sender side is repeated and the addressee side is not,
and a consumer must not flatten the first to a single value. A Matter with two
senders contributes to both of their segments, so counts grouped by sender do
not partition the population and their total may exceed the number of Matters
(ADR 0025).

## Submission-derived compatibility fields

The current register carries a single "opinion sent" date. In the new model one
Matter may produce several `Submission` records, so the compatibility fields are
**derived** from `Submission`, by a documented and versioned rule, and are not
stored as canonical columns on `Matter`.

| Field | Derivation rule (v1) |
| --- | --- |
| `first_submission_sent_at` | earliest `Submission.sent_at` where `status = SENT` |
| `latest_submission_sent_at` | latest `Submission.sent_at` where `status = SENT` |
| `submission_sent_count` | count of `Submission` rows where `status = SENT` |
| `compat_opinion_sent_date` | `first_submission_sent_at`, for byte-comparability with the register |

Withdrawn and superseded submissions are excluded from all four. Opinion volume
is counted from `Submission`, never from the number of Matters.

## Consultation counts

| Field | Source | Notes |
| --- | --- | --- |
| `consultation_contacted_count` | `Consultation.contacted_count` | Independent observation. Nullable. |
| `consultation_response_count` | `Consultation.response_count` | Independent observation. Nullable. |
| `consultation_count_provenance` | `Consultation.count_provenance` | `LEGACY_IMPORTED`, `NATIVE_MANUAL` or `COMPUTED`. |
| `consultation_population_note` | basis notes | Free text where the source recorded one. |

**These two counts are independent numbers with no guaranteed common
denominator, and this contract does not export a response rate derived from
them.** A native response rate may be added in a future contract version only
when the contacted and response populations are provably compatible and coverage
is sufficient — never for legacy rows.

## Prohibited outputs

This contract will not carry, in any version:

- lawyer productivity or output scoring from Matter or submission counts;
- "workload" inferred from open Matter count;
- a legacy consultation response rate;
- a Koda win rate or any causal influence percentage;
- average Matter duration across mixed process types without segmentation;
- trend lines that silently span a schema-era break.

## Coverage

Every exported aggregate carries its source population, eligible origins and
completeness. Where completeness is below the agreed threshold the value is
reported as *insufficient data*, not as a number. See
`docs/metric-catalog/README.md`.

## Reconciliation before cutover

1. Generate the old register-derived feed and this export for the same agreed
   population.
2. Diff field by field.
3. Classify every mismatch as expected mapping difference, source anomaly or
   defect.
4. Require zero unexplained differences on the agreed sign-off fields.
5. Store the reconciliation report with the migration evidence.
