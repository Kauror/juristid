{% comment %} The five `Kaasamine` fields, shared by the add form and every edit form. One partial rather than two copies, because the add and edit forms are the same five fields and a copy is where they would drift. `record` supplies the current values when editing and is absent when adding. Rendered by hand rather than through `{{ form }}`: an edit form has to show what is stored, and Django's bound-form machinery would need one form instance per row built in the view for that. Five inputs is cheaper than that plumbing. `bound_values` says *this* copy is the one the refused save came from, and it is what makes rendering by hand safe. One bound form is shared by the add form and every row's edit form, so a copy that read `form.data` unconditionally would paint the rejected values across all of them. The caller sets it on exactly one: the add form when the add failed, the edited row when that row failed. Without it the hand-rendered add form showed a blank Pealkiri after a refusal — the view re-renders "so nothing typed is lost" and the template lost it anyway (Kaasamine one-click §7). {% endcomment %} {% comment %} No `value` when adding. The record may be about a consultation from years ago, and a box pre-filled with today is answered by pressing save (brief 38). An unreadable date is also the one refusal this form could make silently: it is the only field the browser will not police on its way out, and its error had nowhere to render, so a rejected save left the box looking exactly as it did before (Kaasamine one-click §7). {% endcomment %}
